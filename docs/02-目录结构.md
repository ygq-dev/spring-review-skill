# Spring Review Skill 目录结构与文件命名规范

文档编号：02  
版本：v0.1  
状态：阶段 A 冻结  
适用范围：只读审查；Java 17+/Spring Boot 3.x；Maven/Gradle；git diff 或指定模块。  
输出：Markdown + JSON。

## 1. 设计原则

- 只读优先：目录不承载自动修改、提交、修复行为；写入模式必须独立目录、独立版本、人工审批。
- 一级分类稳定：规则、示例按 18 个一级分类码组织，分类码使用大写字母。
- 规则与示例分离：规则定义放 `rules/`，正反例放 `examples/`。
- 正反例成对：正例与反例分开目录，文件名与规则编号绑定。
- ID 可追溯：规则编号使用 `SRS-<一级>-<二级>-<三位序号>`，测试用例使用 `TC-<一级>-<三位序号>`。
- Schema 集中：所有 JSON Schema 统一放 `schema/`，并按语义化版本归档。
- 构建文件根置：Maven 与 Gradle 构建文件均放项目根目录。
- 后续可插拔：CI、Spring AI、LangChain4j、Agent 化均使用预留目录，不破坏 MVP 结构。
- 文档中文可读：`docs/`、`handoff/` 使用中文主题与阶段 ID；代码、配置、脚本使用小写英文短横线。
- 目录职责单一：一个目录只承担一类职责，便于冻结、演进和审查。

## 3. 各目录职责说明

| 目录/文件       | 职责                                                      |
| --------------- | --------------------------------------------------------- |
| `docs/`         | 存放项目目标、规范、设计、指南、ADR 等文档。              |
| `handoff/`      | 存放阶段交接摘要与模板。                                  |
| `rules/`        | 存放按一级分类拆分的规则文件与规则索引。                  |
| `examples/`     | 存放按一级分类组织的正例与反例。                          |
| `tests/`        | 存放测试用例、夹具、期望结果、评测集与测试报告。          |
| `schema/`       | 存放 JSON Schema 当前版本与历史版本。                     |
| `scripts/`      | 存放审查、校验、评测、索引生成等脚本。                    |
| `config/`       | 存放 Checkstyle、PMD、ArchUnit、SpotBugs、审查配置等。    |
| `reports/`      | 存放 Markdown、JSON、基线、评测等输出。                   |
| `ci/`           | 预留 CI 配置目录，集成阶段启用。                          |
| `integrations/` | 预留 Spring AI、LangChain4j 等外部集成目录。              |
| `agent/`        | 预留 Agent 化组件、提示词、工具、工作流、审批与写入模式。 |
| `src/`          | 预留实现代码目录，具体 Java 结构后续阶段定义。            |
| `.github/`      | 预留 GitHub 平台级配置，集成阶段启用。                    |
| 根构建文件      | Maven 与 Gradle 构建入口，必须放项目根目录。              |

## 4. 规则文件组织方式

- 规则文件按一级分类组织，每个一级分类一个文件。
- 规则文件路径：rules/<一级分类码>.yaml
- 文件内规则编号：`SRS-<一级分类码>-<二级分类码>-<三位规则序号>`。
- 不按二级分类拆分文件，二级分类只体现在规则编号与元数据中。
- 规则索引放 `rules/index.json`。
- 规则库说明放 `rules/README.md`。
- 正例：rules/AR.yaml、rules/SEC.yaml、rules/DAO.yaml
- 反例：rules/AR.md、rules/AR-01.yaml、rules/security.yaml

## 5. 示例文件组织方式

- 示例按一级分类分目录：`examples/<一级分类码>/`。
- 正例与反例分开：`examples/<一级分类码>/positive/`、`examples/<一级分类码>/negative/`。
- 示例文件名与规则编号绑定：`SRS-<一级>-<二级>-<三位序号>_positive.<ext>`、`SRS-<一级>-<二级>-<三位序号>_negative.<ext>`。
- 扩展名按示例类型使用，如 `.java`、`.xml`、`.yml`、`.properties`。同一规则的正例和反例扩展名应一致，除非规则本身跨多种文件类型。
- 每个一级分类目录放 `README.md`，说明该分类示例约定。
- 正例：`examples/AR/positive/SRS-AR-01-001_positive.java`。
- 反例：`examples/AR/negative/SRS-AR-01-001_negative.java`。
- examples/index.json：示例索引，列出所有正例和反例文件及其对应规则编号。

## 6. 测试用例组织方式

- 测试用例统一放 `tests/cases/`。
- 测试用例 ID 格式：`TC-<一级分类码>-<三位序号>`。
- 测试用例文件命名：`TC-<一级分类码>-<三位序号>.json`。
- 测试用例索引：`tests/cases/index.json`。
- 测试夹具放 `tests/fixtures/`。
- 期望结果放 `tests/expected/`。
- 评测集放 `tests/evaluation/`。
- 测试报告放 `tests/reports/`。
- 正例：`tests/cases/TC-AR-001.json`、`tests/cases/TC-SEC-012.json`。
- 反例：`tests/cases/TC-AR-1.json`、`tests/cases/TC-AR-01-001.json`、`tests/cases/ar-001.json`。

## 7. Schema 文件组织方式

- 所有 Schema 文件统一放 `schema/`。
- 当前稳定版本放 `schema/` 根目录。
- 历史版本放 `schema/versions/v<semver>/`。
- Schema 命名：`<领域>.schema.json`。
- Schema 索引：Schema 索引，列出当前稳定版本、历史版本、各 Schema 文件及其用途。
- Schema 说明：`schema/README.md`。
- 正例：`schema/rule.schema.json`、`schema/report.schema.json`。
- 反例：`schema/RuleSchema.json`、`schema/rule-schema-v1.json`、`docs/rule.schema.json`。

## 8. 文档组织方式

- 项目文档统一放 `docs/`。
- 顶层文档命名：`docs/<两位序号>-<中文主题>.md`。
- 设计文档放 `docs/design/`。
- 使用指南放 `docs/guides/`。
- 架构决策记录放 `docs/adr/`，命名 `ADR-<四位序号>-<中文主题>.md`。
- 正例：`docs/00-项目目标.md`、`docs/02-目录结构.md`、`docs/adr/ADR-0001-目录结构冻结.md`。
- 反例：`docs/2-目录结构.md`、`docs/目录结构.md`、`docs/adr/adr-1.md`。

## 9. 脚本组织方式

- 脚本统一放 `scripts/`。
- 入口脚本放 `scripts/` 根目录。
- 公共函数放 `scripts/lib/`。
- 模板放 `scripts/templates/`。
- 写入类脚本独立放 `scripts/write/`，默认不启用。
- 脚本命名：`<动作>-<对象>.sh`、`<动作>-<对象>.ps1`。
- 正例：`scripts/review.sh`、`scripts/validate-rules.sh`、`scripts/run-evaluation.sh`。
- 反例：`scripts/validateRules.sh`、`scripts/rule_validate.sh`、`scripts/review.bash`。

## 10. 交接摘要组织方式

- 交接摘要统一放 `handoff/`。
- 阶段摘要命名：`handoff/<阶段ID>.md`。
- 阶段 ID 使用大写字母加数字，如 `A1`、`A2`、`A3`。
- 模板放 `handoff/TEMPLATE.md`。
- 历史归档放 `handoff/archive/`。
- 正例：`handoff/A1.md`、`handoff/A2.md`、`handoff/A3.md`。
- 反例：`handoff/a3-summary.md`、`handoff/A3-交接.md`、`handoff/阶段A3.md`。

## 11. 构建文件位置

- Maven 与 Gradle 构建文件均放项目根目录。
- Maven：`pom.xml`、`mvnw`、`mvnw.cmd`。
- Gradle：`build.gradle`、`settings.gradle`、`gradle.properties`、`gradlew`、`gradlew.bat`。
- 构建输出目录不纳入规范结构，如 `target/`、`build/`、`.gradle/`。
- 第一版同时支持 Maven 和 Gradle，不将构建文件放入子模块。
- 正例：根目录 `pom.xml`、根目录 `build.gradle`。
- 反例：`spring-review-skill/pom.xml`、`build/maven/pom.xml`。

## 14. 目录演进规则（MVP → 增强 → 集成 → Agent 化）

| 阶段     | 新增或启用目录                                               | 规则                                                   | 兼容要求                                                     |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------ | ------------------------------------------------------------ |
| MVP      | 本文件第 13 章目录树                                         | 只读审查；规则、示例、测试、Schema、脚本、构建文件冻结 | 不移动已冻结路径；一级分类不变                               |
| 增强     | `config/spotbugs/`、`tests/evaluation/`、`reports/evaluation/`、`scripts/validate-spotbugs.sh` | 增加 SpotBugs；评测集与评测报告独立                    | 不改变 `rules/`、`examples/`、`tests/cases/` 命名            |
| 集成     | `ci/`、`.github/workflows/`、`integrations/`、`config/ci/`、`reports/ci/` | 接入 CI；CI 默认只读调用审查；外部集成目录启用         | CI 不直接修改代码；报告仍输出 Markdown + JSON                |
| Agent 化 | `agent/`、`agent/prompts/`、`agent/tools/`、`agent/workflows/`、`agent/approvals/`、`agent/write-mode/`、`integrations/spring-ai/`、`integrations/langchain4j/`、`reports/agent/` | 接入 Spring AI 或 LangChain4j；Agent 默认只读          | 写入模式必须独立版本、独立目录、人工审批；审批记录放 `agent/approvals/` |
| 所有阶段 | 不移动既有目录                                               | 新增目录优先使用预留目录；命名规范保持兼容             | 旧规则编号、测试用例 ID、Schema 版本不可被覆盖               |
