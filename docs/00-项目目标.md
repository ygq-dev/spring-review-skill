# 00-项目目标

> 项目：Spring Review Skill  
> 阶段：阶段 A / 任务 A1  
> 状态：冻结版 v0.2  
> 文档用途：定义项目目标、边界、量化成功标准与阶段规划

## 1. 项目名称

Spring Review Skill（Spring 代码审查 Skill）

## 2. 一句话描述

一个只读的 Spring 代码审查 Skill：把 Spring 学习笔记提炼为规则库，结合 Checkstyle、PMD、SpotBugs、ArchUnit、JGit、Maven/Gradle、CI 与大模型，对 git diff 或指定模块输出可追溯、可评测、可版本化的审查报告。

## 3. 背景与动机

- Spring / Spring Boot 项目规范多，涉及分层架构、依赖注入、事务、异常、日志、配置、安全、测试等，团队经验不一致。
- 人工代码审查成本高，容易漏项，审查结论依赖个人经验，难以沉淀和复用。
- 通用大模型直接审查代码时，存在幻觉、标准漂移、输出不稳定、无法追溯规则来源等问题。
- Checkstyle、PMD、SpotBugs、ArchUnit 能发现部分问题，但缺少 Spring 语义规则、审查工作手册和统一输出协议。
- 已有 Spring 学习笔记尚未结构化，无法直接用于审查、评测和版本管理。
- 需要构建一个 Skill，把“规则库 + 工作手册 + 工具调用 + 输出协议 + 审查流程 + 评测与版本管理”组合起来，形成可维护、可验收的代码审查能力。

## 4. 目标（要解决什么问题）

| 目标 ID | 目标               | 验收标准                                                     |
| ------- | ------------------ | ------------------------------------------------------------ |
| G1      | 建立 Spring 规则库 | MVP 至少 40 条规则，覆盖至少 8 类问题；每条规则包含 ID、名称、严重级别、适用条件、正例、反例、来源、检测方式 |
| G2      | 支持只读审查       | 可审查 git diff 或指定模块；审查过程不修改代码、不提交、不推送 |
| G3      | 集成静态分析工具   | 可调用 Checkstyle、PMD、ArchUnit、JGit；增强阶段加入 SpotBugs；工具结果可合并进审查报告 |
| G4      | 定义统一输出协议   | 输出 Markdown 和 JSON；JSON 100% 符合预定义 Schema；每条问题包含规则 ID、文件、行号、证据、置信度、建议 |
| G5      | 建立审查工作手册   | 明确审查步骤、提示词模板、工具调用顺序、结果合并规则、人工确认节点 |
| G6      | 建立评测机制       | 至少 30 个基准案例；对预置缺陷检出率 ≥ 80%；对正常代码误报率 ≤ 20% |
| G7      | 建立版本管理       | 规则库、Skill、提示词、工具配置均有语义化版本；变更可追溯、可回滚 |
| G8      | 支持 CI 与本地运行 | 提供 Maven/Gradle/CI 示例，10 分钟内可跑通一次只读审查       |

## 5. 范围（做什么）

| 范围项   | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 审查模式 | 第一版只做只读审查                                           |
| 审查对象 | Java / Spring / Spring Boot 项目；git diff；指定模块或目录   |
| 规则来源 | Spring 学习笔记、团队规范、官方最佳实践、静态工具规则        |
| 规则类型 | 分层架构、依赖注入、事务、异常处理、日志、配置、安全、测试、API 设计、性能反模式 |
| 工具调用 | Checkstyle、PMD、ArchUnit、JGit；增强阶段加入 SpotBugs       |
| 构建工具 | Maven、Gradle                                                |
| 输出格式 | Markdown 审查报告、JSON 结构化结果                           |
| 审查流程 | 获取 diff → 解析项目 → 调用工具 → 规则匹配 → 大模型解释 → 合并去重 → 输出报告 |
| 工作手册 | 审查步骤、提示词、工具使用说明、输出协议、人工复核流程       |
| 评测     | 基准案例、检出率、误报率、回归测试                           |
| 版本管理 | 规则版本、Skill 版本、提示词版本、工具配置版本               |
| CI 集成  | 提供 CI 示例，支持手动触发或 PR 触发只读审查                 |

## 9. 约束条件

- 只读审查，不修改目标仓库任何文件。
- 第一版优先支持 Java 17+、Spring Boot 3.x。
- 第一版支持 Maven、Gradle 项目。
- 工具版本需锁定，避免规则漂移。
- 大模型调用需可配置，优先支持本地或私有化部署。
- 审查输入仅支持 git diff 或指定模块。
- 输出必须机器可解析，JSON 是主要结构化格式。
- 规则来源必须可追溯，不允许编造规范。
- 敏感代码需支持脱敏或本地处理。
- 审查耗时、令牌成本、并发数需可配置。
- 第一版不默认阻断 CI，只输出报告和退出码选项。

## 10. 假设与依赖

- 目标项目位于 Git 仓库中。
- 目标项目有可用的 Maven 或 Gradle 构建。
- 目标代码可编译，或至少可被解析。
- Checkstyle、PMD、ArchUnit 可配置并输出结果。
- 增强阶段 SpotBugs 可配置并输出结果。
- 存在可提炼的 Spring 学习笔记和团队规范。
- 可调用大模型 API，或部署本地模型。
- CI 环境可安装 Java、Maven/Gradle 和静态分析工具。
- 用户接受只读审查，并愿意人工确认最终结论。
- 规则库维护者持续评审和更新规则。

## 11. 风险与对策

| 风险         | 影响         | 对策                                   |
| ------------ | ------------ | -------------------------------------- |
| 规则覆盖不足 | 审查价值低   | MVP 聚焦高频问题，按迭代扩展           |
| 误报率高     | 用户不信任   | 增加置信度、严重级别、白名单、人工确认 |
| 模型幻觉     | 输出错误结论 | 工具事实优先，规则约束，必须引用证据   |
| 审查性能慢   | 无法进入 CI  | 只审查 diff、缓存、并行、限制上下文    |
| 工具版本冲突 | 结果不一致   | 统一版本，提供容器化或配置模板         |
| 安全隐私     | 代码泄露     | 本地模型优先，脱敏，只读，最小权限     |
| 评测不足     | 质量不可衡量 | 建立基准集，持续回归                   |
| 规则漂移     | 标准不一致   | 规则版本化，变更评审，变更日志         |
| 用户不采纳   | 项目失败     | 输出可操作建议，CI 示例，阈值可配置    |
| 模型成本高   | 难以持续     | 规则前置过滤，只把可疑片段交给模型     |

## 14. 冻结结论

本项目第一版定位为：**只读、可追溯、可评测、可版本化的 Spring 代码审查 Skill**。  

说明：

第 6 节禁止清单仅约束 MVP / 第一版。集成阶段如要引入 IDE 插件或平台 API，
必须作为独立版本重新评审，并明确写入模式、权限模型和人工审批流程。

S5、S6 的测量依赖 B/C 阶段建立的基准评测集；在评测集建立前，
这两个指标标记为“待测量”，不作为 MVP 早期退出门槛。

冻结说明：本文档为 A1 冻结版。后续如需修改目标、范围、非范围或成功标准，
必须走变更记录流程，记录变更原因、影响范围和回滚方式。

第一版只审查 git diff 或指定模块，只输出审查报告和建议，不自动修改代码。  
所有后续规则、工具、提示词、输出协议和评测，均以本文档定义的目标、边界、量化成功标准和禁止清单为准。
