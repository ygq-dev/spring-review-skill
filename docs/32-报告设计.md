# docs/32-报告设计.md

> 阶段：E10 报告设计（M14、M15、M16、M17）  
> 范围：只读审查报告生成、校验、输出、归档。  
> 契约来源：docs/23-31、SKILL.md、A5、A6、E2、E3、E9。  
> 约束：不修改代码、不提交、不训练模型；不修改 A5/A6；不修改 B1～B7；不修改 SKILL.md、docs/23～31；不新增 E3 未冻结配置字段。

## 1. 设计原则

1. **A6 Schema 单一事实源**：`ReviewReport` 顶层、`scope`、`summary`、`issues[]`、`tool_runs[]`、`metrics` 严格对齐 `schema/review-report.schema.json`，不新增顶层字段，`additionalProperties: false` 优先。
2. **M13 后置不重算**：M14/M15/M16/M17 不重新去重、不重新排序、不重新合并置信度；`issues[]` 顺序、`issue_id`、枚举合法性以 M13 输出为准。
3. **JSON 主产物，Markdown 可降级**：JSON 生成、写入、校验失败退出 5；Markdown 生成失败仅告警，不影响 JSON 输出。
4. **同源一致**：Markdown 只消费 M14 生成的 `ReviewReport`，不独立计算摘要、指标、问题列表；JSON 与 Markdown 内容一致。
5. **最小写入与原子更新**：只写 `output.dir/latestDir/historyPattern`；UTF-8；先写临时位置，再原子替换；Windows 11 下强制 UTF-8，避免 GBK 默认。

## 2. M14 JSON 报告生成

### 2.1 接口契约

| 接口                                    | 输入                                                         | 输出                    | 主要异常                                                 | 退出码 |
| --------------------------------------- | ------------------------------------------------------------ | ----------------------- | -------------------------------------------------------- | ------ |
| `generate(ReportInput) -> ReviewReport` | `ReportInput`：scope、issues、toolRuns、summary、metrics、可选 reportId/generatedAt/metadata | `ReviewReport`，符合 A6 | `ReportGenerationException`、`ReportValidationException` | 失败 5 |
| `toJson(ReviewReport) -> String`        | 已生成 `ReviewReport`                                        | JSON 字符串，UTF-8 语义 | `ReportSerializationException`                           | 失败 5 |
| `writeJson(ReviewReport, Path) -> void` | `ReviewReport`、目标文件路径                                 | 写入 JSON 文件          | `ReportWriteException`                                   | 失败 5 |

### 2.2 行为契约

- `generate`：
  - 生成或校验 `report_id`、`generated_at`；若 `ReportInput` 显式提供则使用并提供幂等基础。
  - report_id 生成规则：
    - 格式：`RPT-<YYYY>-<4 位数字>`
    - `YYYY` 取 `generated_at` 的 UTC 年
    - 4 位数字为当天流水号，从 `0001` 开始
    - 若同日历史归档已有 N 个报告，则本次为 N+1
    - 若 `ReportInput` 显式提供 `report_id`，则使用并提供幂等基础，且必须校验符合 A6 pattern
  - 组装 A6 `ReviewReport`；不执行规则、不调用 LLM、不重算 summary/metrics。
  - 调用 M17 `validateOrThrow`；校验失败退出 5。
- `toJson`：
  - Jackson 序列化；字段顺序稳定；UTF-8；不输出 `null` 可选字段，除非 A6 要求保留。
  - 同一 `ReviewReport` 多次调用结果稳定。
- `writeJson`：
  - 写入临时文件后原子移动到目标；同路径覆盖；调用方负责目录存在或由本接口创建。
  - 不负责 `reports/latest`、`reports/history` 组织，该职责归 M16。

### 2.3 异常契约

- 输入缺失 A6 必填字段：`ReportGenerationException`，退出 5。
- M17 校验失败：`ReportValidationException`，退出 5。
- Jackson 序列化失败：`ReportSerializationException`，退出 5。
- 文件写入失败：`ReportWriteException`，退出 5。

### 2.4 幂等性与线程安全

- 幂等性：
  - `toJson` 对同一不可变 `ReviewReport` 幂等。
  - `writeJson` 同路径覆盖，最终内容一致。
  - `generate` 若 `ReportInput` 提供固定 `report_id` 与 `generated_at`，则幂等；否则每次生成新 ID/时间。
- 线程安全：
  - M14 不持有可变共享状态；Jackson `ObjectMapper` 配置完成后只读。
  - `writeJson` 对同一路径并发写需外部串行；M16 保证归档与 latest 更新串行。

## 3. ReviewReport 结构（对齐 A6）

### 3.1 顶层

| 字段             | 必填 | 说明                                                         |
| ---------------- | ---- | ------------------------------------------------------------ |
| `report_id`      | 是   | 报告唯一 ID；必须匹配 A6 pattern `^RPT-\d{4}-\d{4}$`，例如 `RPT-2026-0001`。M14 生成规则见 2.2 节。 |
| `schema_version` | 是   | 与 A6 对齐；当前设计按 A6 冻结版本读取                       |
| `generated_at`   | 是   | ISO-8601 UTC，如 `2026-09-25T12:34:56Z`                      |
| `scope`          | 是   | A6 scope                                                     |
| `summary`        | 是   | A6 summary                                                   |
| `issues`         | 是   | A6 issue 数组                                                |
| `tool_runs`      | 是   | A6 tool_runs 数组                                            |
| `metrics`        | 是   | A6 metrics                                                   |
| `metadata`       | 否   | 仅放非顶层扩展信息：生成器版本、警告、脱敏计数、LLM 调用记录摘要等 |

`additionalProperties: false`：不得新增 A6 未允许的顶层字段。

### 3.2 scope

必填：`mode`、`project`、`base_ref`、`head_ref`、`paths`、`diff_lines`。  
`mode` 枚举：`DIFF`、`MODULE`、`FILES`。

### 3.3 summary

必填：`total_issues`、`by_severity`、`by_category`、`blocking`、`duration_ms`、`token_usage`。  
M14 不重算；直接使用 M13 输出的 A6 summary 来源。

### 3.4 issues[]

必填：`issue_id`、`rule_id`、`severity`、`confidence`、`detection_method`、`file`、`line`、`column`、`evidence`、`message`、`remediation`。  
可选：`tool`、`tool_rule_id`、`test_case_id`、`snippet`、`fingerprint`、`first_seen_at`、`last_seen_at`、`issue_status`、`tags`。  
`issue_id` 格式：`ISSUE-<8 位大写十六进制>`。

枚举：
- `severity`：`BLOCKER`、`CRITICAL`、`MAJOR`、`MINOR`、`INFO`
- `confidence`：`HIGH`、`MEDIUM`、`LOW`
- `detection_method`：`STATIC_ANALYSIS`、`AST`、`ARCH_TEST`、`RULE_ENGINE`、`REGEX`、`HEURISTIC`、`HYBRID`、`MANUAL`

### 3.5 tool_runs[]

必填：`tool`、`tool_version`、`status`、`started_at`、`ended_at`、`duration_ms`、`exit_code`。  
可选：`issues_count`、`error_message`。  
`tool` 枚举：`CHECKSTYLE`、`PMD`、`ARCHUNIT`、`SPOTBUGS`、`CUSTOM`。  
`status` 枚举：`SUCCESS`、`FAILED`、`SKIPPED`、`TIMEOUT`。

### 3.6 metrics

必填：`total_files_scanned`、`total_lines_scanned`、`duration_ms`、`tool_success_rate`。  
可选：`cache_hit_rate`、`llm_calls`、`by_severity`、`by_category`。

## 4. M15 Markdown 报告生成

### 4.1 接口契约

| 接口                                 | 输入                          | 输出               | 主要异常                      | 降级                    |
| ------------------------------------ | ----------------------------- | ------------------ | ----------------------------- | ----------------------- |
| `generate(ReviewReport) -> Markdown` | 已校验或已生成 `ReviewReport` | Markdown 文本      | `MarkdownGenerationException` | 可关闭；失败不影响 JSON |
| `renderSummary(Summary) -> Markdown` | A6 `Summary`                  | 摘要 Markdown 片段 | `MarkdownGenerationException` | 仅局部失败              |

### 4.2 行为契约

- 只读 `ReviewReport`；不重新计算 `summary`、`metrics`、`issues`。
- 使用 Java 文本块拼接；不引入模板引擎。
- 生成前不得再调用 M17；M16 负责写前最终校验。
- Markdown 内容必须可由 JSON 字段追溯。

### 4.3 异常契约

- Markdown 生成失败：记录警告，继续输出 JSON。
- 若 Markdown 被关闭：跳过生成，不视为失败。
- Markdown 失败不单独映射退出码 5；除非主流程其他阶段失败。

## 5. Markdown 报告格式设计

### 5.1 章节结构

1. `# Spring Review Report`
2. `## 元信息`
3. `## 范围`
4. `## 摘要`
5. `## 问题`
6. `### BLOCKER / CRITICAL / MAJOR / MINOR / INFO`
7. `## 工具运行`
8. `## 豁免`
9. `## 人工确认`
10. `## 指标`
11. `## 附录：元数据与警告`

### 5.2 字段展示与一致性

| Markdown 部分 | JSON 来源                                                | 一致性要求                                   |
| ------------- | -------------------------------------------------------- | -------------------------------------------- |
| 元信息        | `report_id`、`schema_version`、`generated_at`            | 原值展示                                     |
| 范围          | `scope.mode/project/base_ref/head_ref/paths/diff_lines`  | 不重算                                       |
| 摘要          | `summary.*`                                              | 与 JSON 相同                                 |
| 问题          | `issues[]`                                               | 组内保持原数组顺序；组间按 severity 固定顺序 |
| 工具运行      | `tool_runs[]`                                            | 原顺序展示                                   |
| 豁免          | `issues[]` 中 `issue_status`/`tags` 表达豁免的条目       | 不新增字段；值以 M13 输出为准                |
| 人工确认      | `detection_method=MANUAL` 或 `tags` 含人工确认语义的条目 | 不新增字段；值以 M13 输出为准                |
| 指标          | `metrics.*`                                              | 与 JSON 相同                                 |

### 5.3 问题条目模板

每个 issue 展示：
- `issue_id`、`rule_id`、`severity`、`confidence`、`detection_method`
- `file:line:column`
- `message`
- `evidence`
- `remediation`
- 可选：`tool`、`tool_rule_id`、`test_case_id`、`snippet`、`fingerprint`、`first_seen_at`、`last_seen_at`、`issue_status`、`tags`

Markdown 不增加 JSON 中不存在的问题字段。

## 6. M16 报告输出与归档

### 6.1 接口契约

| 接口                                                         | 输入                                  | 输出              | 退出码     |
| ------------------------------------------------------------ | ------------------------------------- | ----------------- | ---------- |
| `write(ReviewReport, Markdown, AppConfig) -> OutputArtifacts` | `ReviewReport`、Markdown、`AppConfig` | `OutputArtifacts` | 写失败 5   |
| `archive(ReviewReport, Markdown) -> ArchiveRef`              | `ReviewReport`、Markdown              | `ArchiveRef`      | 归档失败 5 |
| `updateLatest(OutputArtifacts) -> void`                      | `OutputArtifacts`                     | 更新 latest       | 更新失败 5 |

### 6.2 目录组织

严格使用 E3 冻结配置：
- `output.dir`：默认 `reports`
- `output.latestDir`：默认 `reports/latest`
- `output.historyPattern`：默认 `reports/history/YYYY/MM/DD/<report_id>/`
- `output.formats`：默认 `[markdown, json]`

固定文件：
- `reports/latest/review-report.json`
- `reports/latest/review-report.md`
- `reports/history/YYYY/MM/DD/<report_id>/review-report.json`
- `reports/history/YYYY/MM/DD/<report_id>/review-report.md`

不新增 E3 未冻结配置字段。

### 6.3 写入顺序

1. 写 history 临时目录。
2. 校验 JSON 后原子移动到 history 正式目录。
3. 写 latest 临时目录。
4. 原子替换 latest。
5. 返回 `OutputArtifacts`。

### 6.4 原子更新策略

- 单文件：写 `*.tmp-<uuid>`，`ATOMIC_MOVE` 替换。
- 目录：写 `latest.tmp-<uuid>`，再替换 `latest`；Windows 下先关闭所有句柄。
- 并发：M16 对同一输出目录串行化。
- UTF-8：所有文本强制 UTF-8，不依赖平台默认 GBK。

## 7. M17 报告校验

### 7.1 接口契约

| 接口                                     | 输入      | 输出                                          | 异常                        | 退出码     |
| ---------------------------------------- | --------- | --------------------------------------------- | --------------------------- | ---------- |
| `validate(JsonNode) -> ValidationResult` | JSON 报告 | `ValidationResult`：valid、errors、errorPaths | 无                          | 不直接退出 |
| `validateOrThrow(JsonNode) -> void`      | JSON 报告 | void                                          | `ReportValidationException` | 失败 5     |

### 7.2 networknt 集成

- 使用 `networknt json-schema-validator 1.4.0`。
- 加载 `schema/review-report.schema.json`。
- `JsonSchema` 对象可缓存；线程安全只读。
- 校验 A6：顶层必填、`additionalProperties: false`、枚举、`issue_id` 格式、数组项必填。

### 7.3 失败处理

- 默认开启；调试可关仅限内部/测试，不新增用户配置字段；如需用户配置走 E2 配置清单评审。
- 校验失败输出错误路径；退出码 5。
- M14 `generate` 后调用；M16 写前再次调用。

## 11. 报告内容脱敏

- 与 E3 脱敏规则对齐；M14 作为报告落盘前最后防线。
- 必脱敏：
  - 密钥、API Key、Token、Password、Secret。
  - `Authorization`、`Cookie`、`Set-Cookie`。
  - 私钥块：`-----BEGIN PRIVATE KEY-----` 等。
  - 常见云厂商凭证模式。
- `metadata` 中的所有字符串值同样按上述规则脱敏；`metadata` 中禁止出现 prompt 原文、response 原文、密钥明文。
- 敏感代码片段：
  - `evidence`、`snippet`、`message`、`remediation`、`tool_runs.error_message`、`metadata` 中命中敏感模式时替换为 `[REDACTED]`。
  - 局部命中局部替换；整段高敏感时整段替换。
- 不改变：
  - `issue_id`、`rule_id`、`severity`、`confidence`、`detection_method`、`file`、`line`、`column`、`fingerprint`、枚举。
- 脱敏计数可放 `metadata.redaction_count`；不新增 A6 顶层字段。

## 12. 报告一致性

- JSON 与 Markdown 同源：Markdown 只读 `ReviewReport`。
- 顶层必填字段必须存在且合法。
- 枚举合法：severity、confidence、detection_method、tool、status、scope.mode。
- `issue_id` 格式合法：`ISSUE-<8 位大写十六进制>`。
- M14/M15/M16/M17 不重新去重、不重新排序、不重新合并置信度。
- Markdown 按 severity 分组展示时，组内保持 M13 原顺序；JSON `issues[]` 原顺序不变。

## 13. 异常与降级

| 场景              | 行为              | 退出码   |
| ----------------- | ----------------- | -------- |
| JSON 生成失败     | 终止报告流程      | 5        |
| Markdown 生成失败 | 告警，继续 JSON   | 不单独 5 |
| 写文件失败        | 终止              | 5        |
| 归档失败          | 终止              | 5        |
| latest 更新失败   | 终止              | 5        |
| M17 校验失败      | 终止              | 5        |
| Markdown 关闭     | 跳过，不影响 JSON | 不单独 5 |

退出码 5 统一表示报告/输出/校验失败。

## 14. 性能与规模

- 目标：数百 issue 下，M14 JSON 生成 < 500ms；M15 Markdown < 300ms；M17 校验 < 300ms；本地 SSD 写入 < 500ms。
- 避免 O(n²)；按数组线性遍历。
- 大报告可先内存树再序列化；不引入模板引擎。
- 归档与 latest 更新原子性优先于吞吐；同一输出目录串行。
- 历史归档保留策略：默认不自动删除；外部运维清理；不新增 E3 配置字段。
- 如需配置化清理策略（保留 N 天或 N 份），走 E2 配置清单评审。

## 15. 报告版本与兼容

- `schema_version` 与 A6 冻结版本对齐。
- `schema_version`：M14 固定写 A6 冻结版本 `1.0.0`。若 A6 未来升版，由 A6 变更评审决定。
- A6 主版本不兼容时，M17 必须拒绝；次版本新增可选字段时，M15 对缺失可选字段容错。
- 不修改 A6；若需新字段，先走 A6 Schema 变更评审。
- 旧报告读取：M15 仅展示已知字段，未知可选字段忽略或放附录。

## 17. 测试策略

- M14：字段完整性、枚举、issue_id、序列化稳定性、幂等、异常映射。
- M15：章节快照、JSON/Markdown 一致性、可选字段缺失容错、降级。
- M16：临时目录、原子替换、Windows 文件句柄、UTF-8、latest/history 路径。
- M17：正例、反例、`additionalProperties`、错误路径、networknt 1.4.0 版本固定。
- 脱敏：密钥、Authorization、Cookie、私钥、敏感片段。
- 集成：M13 输出到 M16 落盘全链路；退出码 5 场景。
- 性能：数百 issue 基准；并发写入串行化。

## 18. 未决问题

1. `metadata` 内部 schema 是否需 A6 明确。
2. `issue_status` 枚举与豁免/人工确认语义是否需 A5/A6 明确。
3. 历史归档保留策略是否需配置化；若需要走 E2 配置清单评审。
4. Windows 下 `latest` 目录原子替换的失败回退策略。
5. 脱敏责任边界：M13 是否先脱敏，M14 是否仅兜底。
6. Markdown 失败是否在 CLI 层作为警告计入摘要。
7. M17 调试关闭开关是否仅内部使用。
